# `/add-feature` — Production Feature Workflow (Design)

- **Date:** 2026-09-23
- **Status:** Draft, awaiting owner review
- **Owner:** vsite founder (solo developer)
- **Scope:** Claude Code tooling only (`.claude/`, `docs/features/`, one small
  version endpoint). No product behaviour changes.

## 1. Goal

The owner gives a feature idea once. The workflow asks every question it
needs in one sitting. It then designs, builds, QAs, releases and verifies the
feature to production with no further input from the owner. There are
exactly three planned human touchpoints:

1. **Intake:** the owner answers one round of questions and signs the Feature Contract.
2. **Design approval:** the owner approves the UI and architecture design, or
   gives feedback, which loops back to design until approved.
3. **Go-live approval:** the owner approves the release before it reaches production.

Any other human input happens only through a **STOP** (§5). A STOP means the
workflow halts, writes down why, notifies the owner and waits. It never guesses.

### Non-goals
- Replacing the per-area `CLAUDE.md` files. The workflow obeys them.
- Microservices. vsite is one Next.js app on DigitalOcean plus Supabase.
  The design phase describes that architecture as it really is. It flags a
  new service only when a feature genuinely needs one, and that is a STOP.
- Agents writing the owner's business numbers.

## 2. Architecture

A single orchestrator skill runs seven phases in sequence. Heavy analysis
goes to specialist subagents. Anything that needs the owner, and anything
that touches production, stays in the main session.

```
/add-feature "<idea>"            (main session = orchestrator)
  │
  ├─ 1 Intake ────────── AskUserQuestion rounds → contract.md  ◆ owner signs
  ├─ 2 Design ─┬─ feature-architect (Opus, read-only) → architecture + impact map
  │            └─ Claude Design (Artifact, intent "design") → UI mockups
  ├─ 3 Approval ─────── present design vN  ◆ owner: approve | feedback → back to 2
  ├─ 4 Build ────────── TDD in worktree feat/<slug> (main session)
  ├─ 5 QA ─────────────┬─ business-qa   (Opus, read-only) → qa-business.md
  │   (parallel)       ├─ technical-qa  (Opus, read-only) → qa-technical.md
  │                    └─ product-tester (local Playwright) → qa-e2e.md
  ├─ 6 Release ──────── merge → tag → build ◆ owner approves → push vsite
  └─ 7 Live verify ──── product-tester on production → severity → rollback / STOP
```

Resuming: `/add-feature` with no argument reads every
`docs/features/*/state.md`. It resumes the single unfinished feature, or asks
which one if several are unfinished.

## 4. Phases

Every phase reads `state.md` first and writes it last. `state.md` holds:
`phase`, `status` (`running` | `awaiting_user` | `stopped` | `done`),
`design_version`, `branch`, `release_tag`, `previous_tag`, and a `log`
list with a timestamp and one line per event.

### Phase 1: Intake
- **In:** the idea text, `CLAUDE.md`, the relevant area `CLAUDE.md` files,
  `business-context.md`, `critical-flows.md`.
- **Do:** read enough code to ask informed questions. Ask **all** questions
  in one sitting, using consecutive AskUserQuestion calls of up to 4
  questions each. Questions cover: the user and the problem, the exact
  behaviour, the areas it touches, Tamil/English copy, edge cases, success
  metrics, cost tolerance, what is out of scope, rollout (flag default off,
  or percentage), and deadline.
- **Out:** `contract.md` containing: goal, acceptance criteria (each one
  testable), non-goals, `approved_sensitive_paths` (usually empty), a feature
  flag name, a cost ceiling, and risk class (low/med/high).
- **Gate:** the owner types "signed". Any answer that later turns out
  ambiguous is a STOP, never a guess.

### Phase 2: Design
- **feature-architect** (Opus) does the following:
  - Refreshes `.claude/docs/architecture.md` from the code-review-graph
    (`get_architecture_overview`, `list_communities`, `get_impact_radius`).
  - Produces:
    1. **Architecture:** routes, lib modules, data model, RPCs, cron jobs,
       env vars, and external calls, as a diagram plus text.
    2. **Existing-user impact map:** every existing flow touched, bucketed
       as `unchanged` / `changed` / `removed-or-replaced`. Each entry reads:
       *"Adding X changes Y; existing owners who use Y will see Z;
       mitigation: …"*
    3. **Migration plan:** expand-only changes (§8), with reversibility shown.
    4. **Critical-flows check:** whether any flow in `critical-flows.md`
       is touched.
    5. **Risks and alternatives considered.**
- **Claude Design:** the main session calls Artifact `quickstart` with
  intent `design`. It produces mobile-first mockups (menu customers are on
  phones), with Tamil and English states, plus empty, error and loading states.
- **Out:** `design-vN.md`, which links the architecture and the Claude
  Design artifact.

### Phase 3: Approval loop
- Present `design-vN`: a summary, the impact map (with
  `removed-or-replaced` items highlighted) and the design link.
- The owner either replies **approved**, or gives feedback. Feedback is
  written into `design-vN.md` under "Feedback", and the workflow returns to
  phase 2 to produce vN+1. There is no round limit.
- Every `removed-or-replaced` item needs its own explicit approval.

### Phase 4: Build (TDD)
- Create a worktree on branch `feat/<slug>` off `master`.
- Follow CLAUDE.md's feature workflow, in this order:
  1. Update GOAL.md.
  2. Write a failing acceptance test in `tests/acceptance/`. Confirm it
     is RED and commit it as `test(<slug>): failing acceptance`.
  3. Write PLAN.md.
  4. Implement until GREEN, re-running the area's suite after every edit.
  5. Refactor.
  6. Update PROGRESS.md and AGENTS.md.
- Additional rules:
  - New behaviour sits behind the contract's flag, **default OFF**.
  - **Backward-compat tests** are mandatory. For each `changed` flow in
    the impact map, a test proves that existing data shapes and existing
    owners' paths still behave exactly as before while the flag is OFF.
  - At most 3 loops on the same failure, then STOP. This is the Ralph cap.
- **Exit:** the full `npx vitest run`, `npx tsc --noEmit` and
  `npm run lint` all pass.

### Phase 5: QA (three reviewers in parallel)
None of the reviewers wrote the code. Each writes a report ending in
`VERDICT: PASS | FAIL | STOP-FOR-OWNER`.

**Business QA** (`business-qa`, Opus):
- Reads `business-context.md`. It STOPs if the file is missing, if a number
  it needs is missing, or if `last_updated` is more than 7 days old.
- Pulls live usage read-only: Supabase DB size, row counts and active shops
  through `SELECT` only. It reads instance size from `.do/app.yaml`.
- Projects the impact per resource, using **existing** users alone as well
  as growth. For each resource it gives: current use / limit → added use per
  shop per month → **runway until exhausted** → the upgrade needed and its cost.
- Unit economics: new fixed cost, new variable cost per shop, the effect on
  margin, and the **additional paying customers needed to break even**.
- Business logic: consistency with the ₹299 single product, the ordering
  freeze and roadmap copy, and INR pricing.
- Every figure is tagged `measured (source)` or `estimated (assumptions)`.
- It STOPs if the cost ceiling is exceeded, any resource runs out within
  90 days, or the break-even requires more customers.

**Technical QA** (`technical-qa`, Opus):
- A line-by-line review of the full diff against `master`.
- A security review: authz on every new route, input validation, RLS and
  service-role usage, secrets, and injection.
- Checks against the CLAUDE.md hard rules: no `any`, no `console.log`,
  protected paths, and the ordering freeze.
- Migration review: expand-only, safe for the previous release to run against.
- Existing-user impact: re-runs the backward-compat tests and runs
  `ordering-frozen` and `paymentAttacks`. It confirms that with the flag OFF
  there is no behaviour change.
- Rollback rehearsal: confirms that the previous release tag builds and
  passes its test suite against the new schema.

**Local E2E** (`product-tester`):
- Runs `npm run dev`, then Playwright on the new feature (happy path, failure
  path, edge cases) and a smoke pass of `critical-flows.md`.
- Uses the test login 1234567890 / OTP 123456.

- **Gate:** all three PASS → phase 6. Any FAIL → back to phase 4, with at
  most 3 loops before a STOP. Any STOP-FOR-OWNER → STOP.

### Phase 6: Release
1. Merge `feat/<slug>` into local `master` (`--no-ff`).
2. Run `npm run build` once. This is the build check before production,
   which the "no build every change" rule allows.
3. Tag `release/<slug>-<YYYYMMDD>`. Record `previous_tag`.
4. Write `release.md` with:
   - a diff summary
   - the three verdicts
   - the impact map
   - the migrations and the order to apply them (the owner applies these;
     agents never do)
   - env vars to set in DigitalOcean
   - the exact push command
   - the exact rollback command
5. **Gate:** present `release.md`. On the owner's yes, run
   `git push vsite master --follow-tags`. The permission is `ask`, so the
   owner clicks again, and `release-guard` must also pass.

### Phase 7: Live verify
- Poll `https://vsite.in/api/version` until it reports the new commit SHA,
  with a 20-minute timeout. A timeout is a STOP.
- `product-tester` runs on production (Claude in Chrome or Playwright):
  - the new feature, with the flag turned on **only for the test shop**
  - a full smoke of `critical-flows.md`
  - the test account and test shop only; it never writes to real
    restaurants' data
- Severity:

  | Severity | Definition | Action |
  |---|---|---|
  | **Critical** | Any flow in `critical-flows.md` is broken | **Auto-rollback** (below), then report |
  | High | The new feature is broken in a way customers can see | STOP: report the impact and a recommendation; the owner decides |
  | Medium/Low | Partial or cosmetic | STOP: report; the owner decides |

- **Rollback** (`rollback.sh <previous_tag>`):
  1. Run `git revert -m 1 <release merge>` on `master`.
  2. Assert that the resulting tree equals `previous_tag`'s tree.
  3. Push to `vsite` (a plain push, not a force push).
  4. Tag `release/rollback-<slug>-<date>`.
  5. Poll `/api/version` again and re-run the critical smoke.

  History is preserved. Because migrations are expand-only, the old code
  runs against the new schema.
- The report goes to `live-verify.md`. For anything short of a clean pass,
  the fix is a new `/add-feature "hotfix: …"` run.
- **Done:** the owner is shown the result, `state.md` is set to
  `status: done`, and PROGRESS.md gets `status: DONE`.

## 5. STOP list

The workflow halts, writes `STOPPED: <reason>` to `state.md`, sends a
desktop notification and waits whenever any of the following happens:

1. A requirement is ambiguous or not covered by the contract.
2. A change is needed to a path not in `approved_sensitive_paths`
   (migrations, `.env*`, payments, auth, `ORDERING_FROZEN`).
3. A new npm dependency is needed.
4. Anything resembles an ordering path (the ordering freeze).
5. A migration is not expand-only.
6. A new external service or paid API is needed.
7. Business QA verdict is `STOP-FOR-OWNER`: over the cost ceiling, runway
   under 90 days, stale or missing business context.
8. An existing test fails for a reason unrelated to the feature.
9. The same failure happens 3 times (the Ralph cap).
10. Any live-verify failure that is not Critical.
11. The deploy is not seen live within 20 minutes.
12. A tool, MCP or browser keeps failing (2–3 attempts, per CLAUDE.md).

## 6. Permissions (`.claude/settings.json`)

- **ask:**
  - `Bash(git push vsite:*)`, `Bash(git push --force:*)`
  - `Bash(doctl:*)`
  - `mcp__plugin_supabase_supabase__apply_migration`
  - `Bash(npm install:*)`, `Bash(npm i:*)`
- **allow:**
  - `Bash(.claude/hooks/rollback.sh:*)`
  - `Bash(npx vitest run:*)`, `Bash(npx tsc --noEmit)`, `Bash(npm run lint)`
  - `Bash(npx playwright test:*)`, `Bash(npm run dev)`
  - read-only git: `status`, `diff`, `log`, `show`, `tag -l`
- **deny:**
  - `Bash(git push origin master:*)`
  - `Bash(supabase db reset:*)`
  - `Bash(rm -rf apps/web/supabase:*)`

Note: `rollback.sh` pushes internally, so the `ask` rule on `git push vsite`
does not fire for it. That is intentional, and it is why hook 2 guards it.

## 7. Hooks

Existing `code-review-graph` hooks are kept unchanged.

| # | Event → matcher | Behaviour |
|---|---|---|
| 1 | PreToolUse → Bash: `release-guard` | For `git push vsite`, block unless: a `release/*` tag is on HEAD; `qa-business`, `qa-technical` and `qa-e2e` all say `VERDICT: PASS`; `release.md` has a rollback command; and the tree is clean |
| 2 | PreToolUse → Bash: `rollback-guard` | Allow `rollback.sh <tag>` only when the tag is an older `release/*` tag and `state.md` records a Critical failure with evidence |
| 3 | PreToolUse → Edit\|Write: `protected-paths` | Block the sensitive paths unless they are listed in the active contract's `approved_sensitive_paths`. Always block writes to `business-context.md` and `critical-flows.md` |
| 4 | PreToolUse → Supabase MCP: `db-readonly` | `execute_sql` allows `SELECT`/`EXPLAIN`/`WITH … SELECT` only. `apply_migration`, `reset_branch`, `delete_branch` and `merge_branch` are denied |
| 5 | Stop: `no-silent-stop` | If a feature is `running` in phase `build`\|`qa`\|`release`\|`live-verify`, block the stop until the phase finishes or a `STOPPED:` entry exists. Allow when `awaiting_user`. Give up after 3 blocks (to avoid a loop) |
| 6 | SubagentStop: `report-check` | For feature-architect, business-qa, technical-qa and product-tester: the report file must exist and contain `VERDICT:`, otherwise the agent is sent back |
| 7 | SessionStart: `resume-hint` | List any unfinished features with their phase |
| 8 | Notification: `toast` | Windows toast when the workflow is waiting for the owner |

Hooks are guardrails, not the trust boundary. The human gate is the `ask`
permission prompt.

## 8. Always-loaded rule: `.claude/rules/release-safety.md`

- Migrations are expand-only per release: add columns and tables, never
  drop, rename or narrow them in the same release. Contract steps happen in
  a later release, once no deployed code reads the old shape.
- Every new behaviour is behind a flag that defaults to OFF.
- The ordering freeze is absolute (see CLAUDE.md).
- Never push to `vsite` outside phase 6 or a Critical rollback.
- Agents never write to `business-context.md` or `critical-flows.md`.

## 9. One-time bootstrap (before the first run)

1. **`/api/version` endpoint:** returns `{ sha }` from the build-time
   commit env var. Built via TDD like any other feature. Needs checking:
   whether DigitalOcean exposes the commit SHA to the build (for example
   `${_self.COMMIT_HASH}` in `.do/app.yaml`). This touches `app.yaml`, so
   the owner's approval is needed.
2. **Baseline tag:** `release/baseline-2026-09-23` on the commit currently
   live on `vsite/master`, so the first release has a rollback target.
3. `.gitignore` gets `.claude/docs/business-context.md`. The owner fills it
   in from the template.
4. The owner reviews `critical-flows.md`. Initial draft: QR menu scan
   (`/shop/[slug]`), login/OTP, `/manage` load, menu edit and sold-out
   toggle, `/api/subscription/verify-payment`.

## 10. Testing the workflow itself

- Unit tests (vitest, `tests/unit/claude-hooks/*.test.ts`) for each hook
  script. Each feeds sample hook JSON on stdin and asserts allow/block and
  the exit code. Covered cases include: push without a tag, push with a
  FAIL verdict, a rollback to a newer tag, a write to `business-context.md`,
  `DELETE` via `execute_sql`, and a Stop while `running` / `awaiting_user`.
- A dry-run feature: a trivial change (for example a footer copy tweak
  behind a flag) run end-to-end through phases 1–6, stopping at the go-live
  gate without pushing. This proves the gates, reports and state resume.
- The skill itself is checked with the `superpowers:writing-skills`
  practice: pressure-test that the orchestrator STOPs rather than guessing.
